# OpenMIND 优化开发计划

> 本文是交给 OpenCode
> 长期执行的项目级计划，明确产品目标、主要开发方法、阶段顺序、依赖和验收原则；不替代详细设计，不预先规定每个文件、函数或
> API 的实现细节。

## 1. 总体目标

在现有 OpenMIND 基础上，完善个人 AI 会议助手，使用户能够完成：

**会前资料准备 → 会中记录与重点标记 → 会后纪要与行动项生成 →**

**个人任务跟进 → 会议资料归档与后续检索。**

在核心闭环稳定后，扩展个人知识库、用户偏好与记忆、按用途配置模型、用户授权的本地会议工作区和音频转写能力。个人使用优先，不因扩展功能而过早引入复杂团队协作体系。

### 总体设计原则

1. **业务闭环优先：**&#x5148;保证现有功能可用、数据一致、来源可追溯，再扩展新能力。
2. **以实际工程为准：**&#x6BCF;次开始工作都检查当前分支、HEAD、工作区、代码和测试。历史审阅报告仅作为线索。
3. **业务驱动、AI 插件式增强：** AI

负责解析、检索、生成候选结果；业务层负责权限、规则校验、状态流转和持久化。AI

不直接操作数据库或任意本地文件。

4. **复用优先、适度演进：** 先理解现有 API、Service、Repository、AI

组件、数据模型和前端页面；优先修复和扩展，不无依据重写架构。

5. **模块职责清晰：**&#x4F1A;前准备、会中记录/转写、会后纪要/行动项、通用对话、知识库、记忆和模型配置边界明确；模型、Prompt、处理策略按用途解耦。
6. **用户可控、结果可追溯：** 区分原始资料、用户编辑内容和 AI

生成结果；关键输出提供来源，允许用户检查和修订；行动项经校验与确认后再转为正式任务。

7. **渐进交付：**&#x6BCF;个阶段交付可运行、可验证的成果，不要求每个小修改都经过用户审批。
8. **安全和数据完整性优先：**&#x7528;户数据严格隔离；密钥安全存储；数据库变化有迁移；危险或不可逆操作需谨慎处理。
9. **验证必须诚实：**&#x533A;分单元测试、Mock、真实数据库/向量检索、真实模型调用和浏览器端到端测试，不得把未执行的验证描述为已通过。

## 2. 项目范围

### 2.1 目标能力

* **首页仪表盘：** 近期会议、会议状态、个人待办和主要功能入口。
* **会议管理：**&#x521B;建、查看、编辑、归档会议；管理会议资料、记录、纪要和相关产物。
* **会前资料预处理：**&#x5BFC;入与预览资料，解析文档，生成背景摘要、议题、议程和个人准备清单；按授权范围检索历史资料。
* **会中记录：**&#x4FDD;存会议文本、手动记录和重点标记，保留时间信息与来源关联；音频转写作为独立能力接入。
* **会后纪要：**&#x878D;合会议记录、相关资料和用户标记；支持模板、编辑、重新生成与导出；重新生成不得静默覆盖已确认内容。
* **行动项和个人任务：**&#x63D0;取候选行动项，校验来源与归属，经确认后进入任务清单；支持编辑、完成、筛选和导出。
* **通用 AI 对话：**&#x652F;持会议问答、资料辅助处理及纪要/任务二次修改；检索范围明确，证据不足时如实说明。
* **模型配置：** 用户配置兼容的大模型接口和密钥，并为不同 AI

用途选择模型；Embedding 维度必须与存储和检索配置一致。

* **个人知识库：**&#x957F;期资料导入、解析、分块、向量化、检索、预览和删除，并可按业务场景使用。
* **记忆中心/用户画像：**&#x7528;户维护职业/角色、工作场景、表达风格和模板偏好；可查看、编辑和删除。
* **本地会议工作区：**&#x7528;户明确授权浏览器访问所选本地目录，用于导入、导出和归档会议资料。
* **音频处理：** 音频导入、转写、文本预览、校正、确认和保存。

### 2.2 范围边界与待确认事项

* 不默认建设复杂团队共享、企业级高可用或大规模并发。
* 不训练自有基础大模型或自研底层 ASR，优先接入兼容服务。
* 不把复杂自主 Agent 或多智能体编排作为基础功能的前置条件。
* 原优化方案要求实时边录边转写，但早期需求曾提出暂不纳入实时监听、先用预录音频演示，存在范围冲突。未确认前，先实现并验证"音频导入

→ 转写 → 预览修订 → 确认保存"，将实时流式 ASR

作为待决策范围，不让其阻塞其他功能。

## 3. 工程基线与权威文档

开发前必须： 1. 检查实际分支、HEAD、远端关系、未提交与未跟踪文件。 2.

保护用户修改；未经授权不执行

reset、clean、覆盖文件、切换分支、merge、rebase、commit 或 push。 3.

阅读 `AGENTS.md`、项目开发规范、本计划和仓库内权威

API、数据库、模块、集成文档。 4. 根据实际代码梳理前端 → API → Service →

Repository/AI → 数据库的关键调用链。 5.

运行适配当前环境的基线测试，记录通过、失败、跳过和未执行项。 6.

复核历史审阅报告中的发现；已修复的不要重复开发，仍存在的才纳入工作。 7.

如果分支不符合预期或现有修改可能被覆盖，先只读审查并报告风险，不擅自合并或"清理"工作区。

以仓库明确指定的

API、数据库文档为契约，不随意另造字段、状态、错误码和数据格式。文档冲突时，先定位权威来源和影响，能依据既有约定解决的，做最小范围统一并同步测试与文档；若涉及产品语义、数据删除、权限或不可逆行为且无法合理推导，应暂停并集中提问。

## 4. 整体开发阶段

阶段是目标和验收边界，不是要求用户逐项下达子任务。OpenCode

可在阶段内自主拆分、合并、排序和连续实施，并根据真实依赖调整顺序；重大调整需说明原因。

### 阶段一：工程基线与关键问题修复

**目标：**&#x5EFA;立可信工程基线，解决阻碍后续开发的安全、契约和数据一致性问题。

**主要方法：** -

复核认证、用户数据隔离、密钥加密、模型配置生效来源等机制。 - 检查

API、Schema、Service、Repository、迁移和前端使用是否一致。 -

复核历史报告指出的风险：问答检索范围与界面说明不一致；会议记录未进入检索；纪要未充分使用相关资料和用户标记；AI

输出的来源记录 ID

未充分验证会议归属；处理状态与同步/异步行为不一致；声明参数未生效；删除关联数据的外键处理；问题状态流转；失败状态与重试语义。 -

上述问题均须按当前代码复核，不可假定仍然存在。 -

必要数据库变更使用迁移并补充回归测试。

**完成标准：**&#x57FA;线和工作区风险清楚；已确认的高优先级安全/数据问题已修复或明确记录暂缓原因；契约一致；相关回归测试通过；不通过删除测试或弱化断言来制造成功。

### 阶段二：完善会议核心业务闭环

**目标：**&#x4ECE;创建会议、导入资料、会前准备、会中记录，到生成纪要、确认行动项和管理任务，形成连续、可追溯的流程。

**主要方法：** -

按真实用户流程和端到端用例组织开发，而不是孤立地按文件或页面开发。 -

明确问答检索范围（当前会议、历史会议或用户明确选择的范围），使界面、请求参数和后端行为一致。 -

在权限范围内检索会议资料和会议记录；回答尽可能提供来源，证据不足时避免编造。 -

纪要融合约定的会议资料、会议记录和用户标记；限制无关全文输入，保留生成版本和用户编辑结果。 -

校验 AI

行动项/问题的来源记录存在且属于当前用户与目标会议；经确认后创建任务，并保持幂等。 -

明确重复生成、失败、重试、状态变更和用户修改的行为；补齐前端加载、空状态、错误和重试提示。

**完成标准：**&#x6838;心流程端到端可运行；来源、归属和状态可验证；重新生成不会静默覆盖已确认内容；重复操作不会产生非预期任务；有可重复自动化测试和手工验收步骤。

### 阶段三：会议体验与 AI 配置增强

**目标：** 提升会议体验，并让 AI 能力可配置、可替换、可测试。

**主要方法：** -

完善用户手动记录、重点/决议/疑问标记及其时间和来源关联。 -

支持正式纪要、简洁记录、任务清单等模板，允许用户编辑。 -

按用途配置模型，例如资料预处理、会前准备、会议问答、纪要生成、行动项/问题提取、音频转写；以现有架构为基础，避免无意义增加配置。 -

复用现有模型配置和调用基础设施，统一处理超时、限流、缺少配置、格式异常和供应商错误。 -

对耗时解析、转写和 AI

任务提供可观察状态、失败原因、重试和幂等策略；只有必要时才引入更复杂的后台任务系统。 -

Prompt 与模型调用按用途解耦，但权限和业务规则不能只靠 Prompt 保证。 -

使用固定样例评估输出质量，区分格式正确、来源正确、行动项提取质量和用户可用性。

**完成标准：**&#x4E3B;要用途的模型选择和回退行为明确；用户标记能进入纪要链路；模板和长任务有可测试、可恢复行为；Embedding

维度与数据库向量列和检索逻辑一致。

### 阶段四：个人知识库与记忆中心

**目标：** 在权限可控的前提下，为 AI 提供长期资料和可管理的用户偏好。

**主要方法：** - 知识库生命周期完整：上传 → 解析 → 分块 → 向量化 → 检索

→ 来源展示 → 删除及索引清理。 -

区分会议资料与个人知识库，按业务场景选择检索范围，避免无关内容自动混入所有回答。 -

处理解析/向量化状态、失败重试、重复导入、文件删除和向量清理。 -

每份资料、分块、向量和检索结果均受用户权限约束，保留可定位来源。 -

记忆中心优先采用用户明确维护的角色、工作场景、表达风格和模板偏好。 -

记忆按任务用途筛选，不得覆盖系统安全规则、事实证据或业务权限；允许用户查看、修改和删除。 -

自动提取的偏好应有确认或可审查机制，避免不知情地积累敏感信息。

**完成标准：**&#x7528;户可独立管理知识库与偏好；检索有来源和权限控制；删除后不再返回已删除内容；证据不足时明确说明；关闭或替换该能力不破坏基础会议功能。

### 阶段五：本地会议工作区与音频

**目标：** 在用户授权下衔接本地资料工作流，并完成可恢复的音频转写流程。

**主要方法：** -

先做可行性验证，确认目标浏览器的目录选择、读写能力、权限生命周期和重新授权方式。 -

不假设后端可直接访问用户电脑的任意绝对路径；本地访问必须基于浏览器授权或明确的本地代理/桌面组件。 -

先实现可控导入/导出，再扩展分类归档和批量操作；定义命名、同名冲突、覆盖、部分失败和重试行为。 -

数据库与本地文件系统不是同一事务，应记录文件操作状态并支持恢复，不能在文件未写入时显示成功。 -

优先完成"选择/上传音频 → 转写 → 查看进度与错误 → 预览修订 → 确认 →

保存会议记录"。 - 实时 ASR

需在产品范围冲突确认后再实现；先验证服务商能力、浏览器采集、流式接口、中断恢复和成本。

**完成标准：**&#x6388;权状态清楚、权限失效可重新授权；文件结果可核验、失败不静默丢失；转写可预览修订并关联会议；实时转写若未完成，文档与界面不得宣传为已支持。

### 阶段六：集成验证与交付

**目标：** 证明系统在约定环境中能完成可重复演示的工作流，而不只是代码或

Mock 测试通过。

**主要方法：** -

运行后端测试、前端类型检查、Lint、测试和构建，并修复回归。 -

在可用环境验证数据库迁移、外键、向量扩展、向量写入和检索。 -

使用有效配置执行真实模型调用，记录测试样例和限制，不泄露密钥。 -

对关键流程进行浏览器

E2E，覆盖成功、空数据、失败、重试、权限不足和重复操作。 -

检查用户数据隔离、密钥保护、错误响应、文件权限、来源校验和日志敏感信息。 -

更新启动、配置、迁移、测试、演示和已知限制文档。 -

外部服务或环境不可用时，明确记录未验证项，不得声称已通过。

**完成标准：**&#x6838;心闭环可重复演示；报告明确区分通过、失败、跳过和未执行；已知问题与启动方式有文档说明；文档和交付物与实际代码一致。

## 5. 跨阶段开发方法

### 5.1 按业务流程推进

每项工作都应考虑：用户要完成什么、流程在哪里中断、数据来源是什么、由谁校验和保存、失败时如何恢复、怎样证明完成。OpenCode

自行拆分内部步骤，不要求用户预先列出。

### 5.2 保持架构边界

* API 层处理请求/响应、认证依赖和参数校验。
* Service 层负责业务流程、权限和归属校验、状态转换与持久化协调。
* Repository 层负责数据访问。
* AI

层负责模型调用、Prompt、解析、检索和候选生成，不直接执行业务写入。

* 前端展示状态、来源、错误、确认和可恢复操作。
* 本地文件访问必须基于明确授权，不允许模型输出路径后由后端任意读写。

以上是职责原则，不要求为了符合描述而机械重构现有目录。

### 5.3 数据库与接口演进

* 数据库变化必须有迁移和测试，不能只改 ORM 模型。
* API 契约变化需同步 Schema、Service、前端调用、测试和权威文档。
* 对状态、删除、重试、幂等和关联关系明确行为。
* 保留已有数据和用户编辑结果；可能导致数据丢失的变更先设计迁移与恢复方案。
* 重大兼容性或产品语义变化需要说明影响，必要时请用户决策；普通实现细节由

OpenCode 自主决定。

### 5.4 AI 输出与安全

* 模型输出视为不可信输入，校验结构、枚举、来源

ID、用户归属和业务状态。

* 不因 Prompt 要求而跳过服务端校验。
* 未经确认，不把 AI 候选结果转成不可逆操作。
* 对外部资料中的指令性内容采取提示注入防护，资料不能覆盖系统规则。
* 日志和错误响应不得泄露密钥、敏感会议全文、内部堆栈或其他用户数据。

### 阶段汇报

阶段结束后统一报告： - 目标与完成情况； - 修改的功能和关键模块； -

重要技术决策及原因； -

测试命令和真实结果（区分单元、Mock、真实服务、E2E）； -

API/数据库/配置/文档变化； - 未解决问题、未验证能力与环境限制； -

是否达到阶段完成标准； - 下一阶段建议和依赖。

汇报不是逐项审批。没有必须人工决策的阻塞问题时，完成当前授权范围内的工作后，给出完整结果并说明下一步。

## 6. 总体依赖与优先级

默认主线：

**工程基线与安全/契约 → 会议核心闭环 → 会议体验和模型配置 →**

**个人知识库与记忆 → 本地工作区与音频 → 集成验收与交付。**

OpenCode

可以并行处理互不冲突的工作或根据实际依赖调整顺序，但应说明重大调整原因。不能为了先做有展示效果的新功能而绕过数据安全、契约一致性或核心业务问题。

优先级原则： 1. 安全、数据丢失、权限越界和核心流程阻断最高。 2.

影响多个模块的契约、数据关系和公共 AI 基础能力优先。 3.

完整业务闭环优先于孤立体验增强。 4.

新能力优先复用已有模型配置、解析、存储和检索机制。 5.

高风险或依赖外部能力的功能先做小型可行性验证。

## 8. 项目整体验收标准

* 用户可创建和管理会议，导入、查看和管理会议资料。
* 会前准备依据选定资料生成摘要/准备内容，失败状态明确。
* 会议记录和用户重点标记可保存，并进入预期后续流程。
* 会议问答有明确检索范围、权限控制和来源；证据不足时不虚构答案。
* 纪要融合约定来源，支持模板、编辑、保存和导出，不静默覆盖已确认内容。
* 行动项经过来源、归属和业务校验；确认后按规则创建任务，重复操作不产生意外重复。
* 个人任务、知识库和记忆可按规则查看、修改或删除，数据归属受到保护。
* 模型配置和调用行为可解释；缺少配置或外部服务失败时有清晰反馈。
* 本地文件和音频功能只在真实实现并验证后标记为可用。
* 后端、前端、数据库、AI 和关键浏览器流程具有与风险相匹配的测试证据。
* 启动、配置、迁移、测试和演示文档与实现一致。

具体数值指标（如行动项精确率/召回率或响应时间）应在固定测试集、测量方法和运行环境明确后设定，不得把没有可重复依据的数字当成已达成标准。
